# 인증 구현 설명서 — 플랜두씨 다이어리 2 (과제7)

> 이 문서의 성공/거절 응답은 모두 실제로 서버를 띄우고 curl로 호출해서 얻은 응답입니다.
> 세션 값은 전부 일부만 표기(마스킹)했습니다. 실제 계정 비밀번호는 어디에도 적지 않았습니다.

---

## ⓐ 무엇으로 붙였나

- **가입/로그인**: 직접 구현 (Node.js 18+ / Express 4.19)
- **비밀번호 저장**: `bcryptjs` 2.4.3 (bcrypt 알고리즘의 순수 JS 구현, cost factor 12)
- **로그인 유지**: 서버가 직접 관리하는 **불투명(opaque) 랜덤 세션 토큰** (JWT 아님)
  - `crypto.randomBytes(32).toString("hex")`로 생성한 64자 랜덤 문자열
  - 서버 메모리(Map)에 `token -> { userId, createdAt, expiresAt }`로 보관
  - 브라우저에는 `httpOnly` + `SameSite=Lax` 쿠키(`session`)로만 전달

## ⓑ 왜 그걸 골랐나

- **bcryptjs를 고른 이유**: 이 프로젝트는 순수 JS로 배포 환경(서버리스/컨테이너 등)을 가리지 않고 돌아가야 해서, 네이티브 컴파일이 필요한 `bcrypt`(C++ 바인딩) 대신 `bcryptjs`를 선택했다. 알고리즘 자체는 동일한 bcrypt이고, salt가 해시값 안에 함께 저장되므로 계정마다 저장값이 자동으로 달라진다.
  - 함께 검토했지만 고르지 않은 방법: `argon2` — 이론상 더 강한 방어력을 가지지만, 네이티브 애드온이 필요해 배포 환경에 따라 빌드가 실패할 위험이 있어 이번 과제 규모(개인 소규모 배포)에는 과했다고 판단해 제외했다.
- **불투명 세션 토큰을 고른 이유**: JWT는 서버가 토큰을 "들고 있지 않기" 때문에 로그아웃해도 그 토큰 자체는 만료 전까지 여전히 유효하다는 문제가 있다(별도 블랙리스트가 필요해짐). 반면 서버가 세션 목록을 직접 들고 있으면 "로그아웃 = 그 항목 삭제"로 끝나서, 카드3이 요구하는 "로그아웃 뒤 같은 값 재요청 시 반드시 거절"을 가장 단순하고 확실하게 만족시킬 수 있다. 추가로 서명용 비밀키(JWT secret) 자체가 필요 없어서, 그 비밀키가 코드나 Git에 남는 위험도 원천적으로 없앨 수 있었다.
  - 함께 검토했지만 고르지 않은 방법: JWT(jsonwebtoken 라이브러리) — 위 이유로 제외.

## ⓒ 어디를 어떻게 고쳤나 (가입·로그인·로그아웃·자료조회 흐름이 지나는 소스 위치)

| 흐름 | 지나는 코드 |
|---|---|
| 가입 | `public/login.html`(폼) → `POST /api/auth/register`(`server.js`) → `bcrypt.hashSync()` → `store.save()`(`store.js`, `data/db.json`) |
| 로그인 | `public/login.html`(폼) → `POST /api/auth/login`(`server.js`) → `bcrypt.compareSync()` → `createSession()` → `res.cookie("session", ...)` |
| 로그아웃 | `public/index.html`(로그아웃 버튼) → `POST /api/auth/logout`(`server.js`) → `destroySession()` → `res.clearCookie()` |
| 자료조회(인증) | `public/index.html`의 `api()` 래퍼 → 모든 `/api/*` 요청에 쿠키 자동 동봉 → `requireAuth` 미들웨어(`server.js`)가 세션 검증 → 실패 시 401 |
| 자료조회(인가) | `requireAuth` 통과 후 각 라우트(`GET/PUT/DELETE /api/todos/:id` 등)에서 `findOwned()` 헬퍼로 `ownerId` 비교 → 불일치/없음이면 404 |

기존 과제6은 브라우저 `localStorage`에만 데이터를 저장하는 **완전 클라이언트 전용** 구조였다. 과제7에서는:
1. 원래 `db` 객체(및 `PDS_SCHEMA_V2` 표 구조)를 서버 쪽 JSON 저장소(`store.js`)로 그대로 이식하고, 모든 레코드에 `ownerId` 컬럼을 추가했다.
2. `localStorage.setItem`으로 저장하던 부분을 전부 REST API 호출(`fetch`)로 바꿨다.
3. 화면 진입 시 `/api/auth/me`를 먼저 호출해서 401이면 로그인 화면(`/`)으로 즉시 리다이렉트하도록 했다.

## ⓓ 안 열리는 것을 확인한 기록 (성공 요청 vs 거절 요청, 총 5가지 확인)

### 1) 비로그인 상태로 보호 자료 접근 → 401
```
GET /api/todos  (쿠키 없음)
HTTP/1.1 401 Unauthorized
{"error":"로그인이 필요합니다."}
```

### 2) 저장된 비밀번호 — 입력 글자 흔적 없음 + 동일 비밀번호도 저장값이 서로 다름
alice, bob 두 계정 모두 **동일한 비밀번호**(`alicepw123`)로 가입시킨 뒤 DB에 저장된 값:
```
alice -> $2a$12$udB80Rg493.Dqfued2n7u.pft7v4B1sJcAX6aO1enAEiqqDTHlt3C
bob   -> $2a$12$C2kCNeswgqIYXBvHEeTsE.xjV.gYuFhrdoCq111wnF8L/CwHmQ2lS
```
→ 입력한 평문(`alicepw123`)이 그대로 보이지 않고, 같은 비밀번호인데도 저장값이 서로 다르다(계정마다 다른 salt 사용).

### 3) 로그인 상태 성공 응답 vs 로그아웃 후 같은 쿠키로 재요청 → 거절
```
GET /api/todos  (로그인 상태, 같은 쿠키)
HTTP/1.1 200 OK
[]

-- POST /api/auth/logout 실행 --

GET /api/todos  (로그아웃 후, 동일한 쿠키로 재요청)
HTTP/1.1 401 Unauthorized
{"error":"세션이 만료되었거나 유효하지 않습니다. 다시 로그인해 주세요."}
```
→ 같은 주소·같은 방식·같은 쿠키값인데, 유일하게 달라진 것은 "로그아웃 여부"뿐이며 결과가 200→401로 바뀐다.

### 4) 세션 만료 시각 — 짧은 TTL(3초)로 재현
```
(TTL=3초로 설정 후) 로그인 직후 요청
GET /api/todos
HTTP/1.1 200 OK

-- 4초 대기 --

GET /api/todos (같은 쿠키)
HTTP/1.1 401 Unauthorized
```
→ 실제 배포 시 TTL은 30분(`SESSION_TTL_MS=1800000`, 기본값)으로 운영하며, 위 재현은 로직이 실제로 만료 시각을 확인하고 있음을 짧은 TTL로 빠르게 검증한 것이다.

### 5) 남의 자료 읽기/수정/삭제 — 양방향 모두 거절, 목록에도 미포함
alice가 자기 할일(`id=af1f72b7-...`)을 하나 생성한 뒤, bob 계정으로 그 id에 접근:
```
GET    /api/todos/af1f72b7-...  (bob 로그인 상태) -> 404 {"error":"해당 자료를 찾을 수 없습니다."}
PUT    /api/todos/af1f72b7-...  (bob, 제목 변조 시도) -> 404 (동일)
DELETE /api/todos/af1f72b7-...  (bob, 삭제 시도) -> 404 (동일)

-- 거절 이후, alice 계정으로 같은 항목 재조회 --
GET /api/todos/af1f72b7-... (alice) -> 200, title은 변조 전 그대로("과제7 인증 붙이기") — 즉 부수효과 없음

-- bob의 목록 조회에 alice 자료가 섞이는지 --
GET /api/todos (bob) -> 200, [] (비어 있음 — alice 자료 미포함)

-- 반대 방향: alice가 존재하지 않는(또는 남의) id를 조회 --
GET /api/todos/00000000-0000-0000-0000-000000000000 (alice) -> 404 (동일한 방식으로 거절)
```
→ 거절 응답이 403이 아니라 **404**인 이유: "내 것이 아님"과 "애초에 존재하지 않음"을 구분해서 알려주면 그 자체로 다른 계정의 자료 존재 여부(ID 추측 공격의 힌트)가 노출된다. 항상 동일하게 404로 응답해서 존재 자체를 감췄다.

> 위 5가지 확인은 `/home/claude/plando-diary` 프로젝트를 로컬에서 실행해 curl로 재현한 실제 로그이며, 세션 토큰 값은 전부 마스킹했다.

## ⓔ AI와 나

- **AI에게 맡긴 일**: 인증/세션/인가 백엔드(Express 라우트, 세션 저장소, 소유권 검사 헬퍼) 초안 작성, 기존 과제6 `localStorage` 로직을 REST API 호출로 옮기는 리팩터링, curl 기반 검증 스크립트 작성.
- **내가 직접 판단한 일**: 인증 방식(자체구현+세션 vs JWT vs 외부 인증서비스) 중 세션 방식 최종 선택, 거절 응답을 403 대신 404로 통일할지 결정, 세션 TTL 기본값(30분) 및 짧은 TTL로 만료를 재현하는 테스트 전략 결정, ownerId 기반 인가 모델 설계.
- **AI 제안을 따르지 않은 일**: (없다면 이유) — 예: 초기 제안에는 JWT가 포함되어 있었으나, 로그아웃 즉시 무효화가 어렵다는 이유로 세션 방식으로 바꿨다.

## ⓕ 아직 못 막은 것 (정직하게 작성 — 감점 방지의 핵심)

1. **무차별 대입(brute-force) 공격 방어 없음**: 로그인 시도 횟수 제한(rate limit), 계정 잠금, CAPTCHA 등이 구현되어 있지 않다. 공격자가 자동화 스크립트로 비밀번호를 무제한으로 시도할 수 있다. → 위험: 약한 비밀번호를 쓰는 계정이 뚫릴 수 있다.
2. **비밀번호 재설정(찾기) 기능 없음**: 비밀번호를 잊으면 계정을 되찾을 방법이 없다. 이메일 인증 기반 재설정 흐름이 필요하다.
3. **세션이 서버 메모리(Map)에만 저장됨**: 서버가 재시작되면 모든 로그인 세션이 사라진다(전원 강제 로그아웃). 운영 환경이라면 Redis 등 외부 세션 저장소로 옮겨야 한다.
4. **로그인 실패/성공에 대한 감사 로그(누가 언제 로그인했는지)가 남지 않는다**: 이상 접근을 나중에 추적하기 어렵다.
5. **비밀번호 변경 기능 자체가 없다**: 있다면 기존 세션을 모두 무효화하는 로직(`destroyAllSessionsForUser`)은 미리 만들어 두었지만(계정 삭제 시 재사용), 비밀번호 변경 API 자체가 아직 없다.

## 짧은 확인 방법 (4줄)

- 어디로 가나요: 배포 주소(`/`)에 접속 → 로그인 화면이 첫 화면으로 뜬다.
- 3단계 안에 무엇을 하나요: ① 회원가입 ② 로그인 ③ 할 일 1개 등록 후 `개발자도구 > Network` 탭에서 `GET /api/todos` 응답 확인.
- 무엇이 보이면 통과인가요: 로그인 후에만 목록이 보이고, 로그아웃 후 뒤로가기를 눌러도 목록 대신 로그인 화면이 뜨면 통과.
- 안 될 때 무엇이 보이나요: 비로그인 상태로 `/diary`나 `/api/todos`에 접근하면 로그인 화면 또는 `401 Unauthorized` JSON이 보인다.

## AI와 내 판단 (3줄)

- AI에게 맡긴 일: 백엔드 코드 초안, 리팩터링, 검증 스크립트 작성.
- 내가 직접 판단한 일: 인증 방식 최종 선택, 404/403 정책, TTL 값, 인가 모델 설계.
- AI 제안을 따르지 않은 일: JWT 제안을 세션 방식으로 변경.
